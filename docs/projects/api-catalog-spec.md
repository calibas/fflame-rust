# The online catalog: what a saved config is, as the database records it

Status: **built 2026-11-11**: client branch `catalog` (`src/catalog.rs`,
`docs/generated/engine-catalog.json`), ffapi branch `catalog` (migration
106, `src/catalog.rs`, `catalog_query`, `routes/types`). Part of
[api-updates.md](api-updates.md) (step 3, and step 4's scripts). The
server is `c:\projects\ffapi` (Postgres; migration 099).

What the user asked for, 2026-11-11:
- filter by **version** (which app can open it);
- filter and **browse by fractal type**: flame, escape-time, simulation;
- find every config that uses **"Mandelbrot"**, the built-in or its
  unedited Rhai twin alike, and the same for simulation models such as
  **Gray-Scott**. An **edited** Rhai script is a type of its own;
- tell **2D from 3D**, terrain included;
- every config the app can make can be saved online (api-updates.md,
  decision 3);
- eventually a Rhai script is **saved separately online**, not inside the
  config. The schema must allow that, though it is not needed yet.

---

## 1. Today

- `flames` has one column read from the config: `render_mode` (a Postgres
  enum: `2d`, `3d`, `escape`). Everything else is the opaque `config`
  JSONB, plus `transforms` rows with a client-sent `variation_names TEXT[]`
  (GIN-indexed).
- Search (`routes/search.rs`) filters by `render_mode`, `has_3d` (=
  `render_mode = '3d'`), `variation`, transform counts and name.
- **The server cannot answer any of the questions above.** It does not know
  which formula or model a config uses, whether an escape or simulation
  config is a terrain or a solid, or which app can open it. `render_mode`
  mixes the engine with the dimension: `escape` says nothing about 2D or
  3D, and simulations have no value at all.

## 2. The facts, per saved config

**Engine**: `flame`, `escape` or `simulation`. This is the top level for
browsing.

**Scene**: what the picture is.

| Scene | Dimension | When |
|---|---|---|
| `plane` | 2D | a 2D flame; an escape formula (mode A) or field (mode B); a simulation's grid |
| `space` | 3D | a 3D flame (`render_mode` ThreeD) |
| `solid` | 3D | an escape solid (mode D: a solid IFS, the Mandelbulb, the Flame Attractor, a Rhai solid) |
| `terrain` | 3D | an escape or simulation terrain in force (`terrain_active()`: switched on, over a plane) |

The dimension follows from the scene. It is stored too, generated by the
database, so "every 3D config" is one indexed filter.

**Versions**: `config_version`, the config version that wrote it, and
`min_reader`, the lowest config version that can read it (api-updates.md
rule 5). A config that predates `min_reader` reads as its `version`.

**Components**: every named piece the picture is made of, each with a
**role** and a **type**:

| Engine | Roles |
|---|---|
| flame | `variation` (each with a non-zero weight, subflames included), `effect` |
| escape | `formula` / `field` / `solid` (what the `formula` slot names, by its kind), `coloring`, `layer_coloring`, `lens` and `transform` (variations), `effect` |
| simulation | `model` (the base) and `layer_model` (each layer's), `coloring` and `layer_coloring`, `effect` |

One component per config is **primary**, the type the config is browsed
under:
- escape: its formula, field or solid;
- simulation: its base model;
- flame: none (a flame is its variations; browsing goes by engine and
  scene, and searching by variation as today).

### A type's identity

| Origin | Key | When |
|---|---|---|
| `builtin` | the registry name: `mandelbrot`, `gray_scott`, `julian` | a built-in, **or its twin unedited** |
| `script` | the script's UUID (`INFO.id`) | a Rhai script with an id of its own |
| `source` | the SHA-256 of the source | any other written source: UF, Fractint, a hybrid, Rhai without an id |

- **A twin unedited is its built-in.** The engine recognises one by its
  source hash. The list of each twin's hashes is **append-only**: when a
  twin's text changes in a release, the new hash is added and the old one
  kept. A config saved with last year's twin still groups under
  `mandelbrot`. A test guards the list, as the texture cache's fingerprint
  is guarded.
- **An edit is a new type.** Edit as Formula, then any change, gives a
  source that is no twin's. Saving it gives it its own UUID
  (`with_own_id`), so it is `script:<uuid>`.
- **A script's versions are one type.** The UUID is the type, and each
  component also records the exact version (the source's SHA-256), so
  "this exact script" can still be asked for. (Decision 2.)
- **When scripts are saved separately** (step 4, P6), the server stores
  scripts under the client's UUID, and the config names `{id, version}`
  instead of carrying the source. A `script` type's key *is* that UUID,
  so the type row gains a link to the `scripts` row and nothing else
  changes: no key moves, no component is rewritten.
- A type carries a **display name**: the built-in's catalog name, or the
  script's `INFO.title`. That lets a search for "Mandelbrot" find the type
  by name, and then every config of it.

## 3. Who works the facts out

**One function in the engine: `fflame::summary(&FractalConfig) ->
Summary`**. It is the only place that knows:
- which escape names are fields or solids;
- when a terrain is in force;
- which sources are twins;
- which variation weights are non-zero.

The `Summary` is a small JSON document: engine, scene, versions,
components (role, origin, key, version, display name, primary), and its
own format version.

Where it runs is decision 1: **the server** ("we shouldn't trust the
client"). **How it gets the engine's knowledge: synced like the contract**
(the user's call, 2026-11-11, over a dependency on the engine crate or a
shared crate):

- The client generates `docs/generated/engine-catalog.json`
  (`UPDATE_CATALOG=1 cargo test --lib catalog_is_current`). It holds the
  **tables** only the engine knows (formula kinds, `needs_flame`, the
  source-kind rules, display names, and every twin's registered name with
  its built-in, append-only), and **examples**: every preset and made-up
  cases (twins, an edit, a script, solids, terrains, a lens, layers,
  effects), each with the summary the client computes.
- `summarize` (`src/catalog.rs` in both repositories) reads only the
  config's JSON and those tables. The server's is a port, and its
  `tests/catalog_conformance.rs` must reproduce every example, so the two
  stay one program. A change to the rules bumps `summary_version`, which
  that test also pins.
- A new built-in, model or twin changes only the tables: copy the file,
  and the server groups it with no code change.
- Every write summarises the stored flame (its blob with its transforms put
  back) in its transaction, and at startup the server summarises every row
  whose `summary_version` is missing or older (`summarize_stale`).
- A twin is recognised by the name it registers under, not by hashing its
  source, and a script by the `u<uuid>_<version>` in its name. The server
  hashes and parses nothing. A custom formula's kind (formula, field or
  solid) comes from the functions its source defines (`source_kinds`,
  `lang::rhai::kind_of`'s order).

## 4. The schema

New columns on `flames`, and two tables. Every enum-like column is
**TEXT with a CHECK**, not a Postgres enum: an enum cannot lose a value,
and adding one needs a migration outside a transaction (the
`ADD VALUE` problem `render_mode` already has). Widening a CHECK is an
ordinary migration.

```sql
ALTER TABLE flames
    ADD COLUMN engine          TEXT,   -- flame | escape | simulation
    ADD COLUMN scene           TEXT,   -- plane | space | solid | terrain
    ADD COLUMN dimension       SMALLINT GENERATED ALWAYS AS
                               (CASE WHEN scene IS NULL THEN NULL WHEN scene = 'plane' THEN 2 ELSE 3 END) STORED,
    ADD COLUMN config_version  INTEGER,
    ADD COLUMN min_reader      INTEGER,
    ADD COLUMN summary_version INTEGER,  -- the summariser that wrote the facets
    ADD CONSTRAINT flames_engine_check CHECK (engine IN ('flame', 'escape', 'simulation')),
    ADD CONSTRAINT flames_scene_check  CHECK (scene IN ('plane', 'space', 'solid', 'terrain'));
CREATE INDEX idx_flames_engine_scene ON flames (engine, scene);
CREATE INDEX idx_flames_min_reader   ON flames (min_reader);

-- A type: a built-in, a script, or a source, of one kind.
CREATE TABLE fractal_types (
    id           BIGSERIAL PRIMARY KEY,
    kind         TEXT NOT NULL,   -- formula | field | solid | coloring | sim_model | sim_coloring | variation | effect
    origin       TEXT NOT NULL CHECK (origin IN ('builtin', 'script', 'source')),
    key          TEXT NOT NULL,   -- registry name | script UUID | source SHA-256
    display_name TEXT,
    script_id    UUID REFERENCES scripts(id) ON DELETE SET NULL,  -- set once scripts are stored apart (P6)
    UNIQUE (kind, origin, key)
);
CREATE INDEX idx_fractal_types_name ON fractal_types USING GIN (to_tsvector('simple', coalesce(display_name, '') || ' ' || key));

-- What a config is made of.
CREATE TABLE flame_components (
    flame_id       UUID   NOT NULL REFERENCES flames(id) ON DELETE CASCADE,
    type_id        BIGINT NOT NULL REFERENCES fractal_types(id),
    role           TEXT   NOT NULL,  -- formula | field | solid | coloring | layer_coloring | lens | transform | model | layer_model | variation | effect
    is_primary     BOOLEAN NOT NULL DEFAULT false,
    script_version TEXT,             -- the exact source SHA-256, for script and source types
    PRIMARY KEY (flame_id, type_id, role)
);
CREATE INDEX idx_flame_components_type ON flame_components (type_id, flame_id);
CREATE UNIQUE INDEX uq_flame_components_primary ON flame_components (flame_id) WHERE is_primary;
```

- **Writes**: summarise, then in the flame's transaction upsert its types
  and replace its components. This is delete-and-reinsert, as transforms
  are done today.
- **`render_mode` stays**, for the old clients' filters and the legacy
  shaping (api-updates.md step 2). It gains `simulation` (decision 3 of
  that plan). `has_3d` keeps its meaning (`render_mode = '3d'`), since
  changing a field's meaning breaks additive rule 1; `dimension` is the new
  axis.
- **`transforms.variation_names` stays** for the existing `?variation=`
  search. Variations are also components, so one type filter covers flames
  and escape lenses alike.
- **Backfill**: existing rows get `config_version` from `config->>'version'`,
  `min_reader` = `config_version`, and engine and scene from `render_mode`
  where that settles it. The escape rows need the summariser run once
  (`summary_version IS NULL`).
- **Animations** inherit browsing through their flame (`flame_id`). Script
  tracks could be components later (kind `track`), if wanted.

## 5. The API

All additive: new query parameters on the existing list and search
routes, and one new route.

```
GET /api/flames?engine=escape&dimension=3&scene=terrain
GET /api/flames?type=mandelbrot                  -- any kind whose built-in key is mandelbrot
GET /api/flames?type=formula:mandelbrot&role=primary
GET /api/flames?type=script:<uuid>[&version=<sha>]
GET /api/flames?reader=7                         -- only what a version-7 reader can open
GET /api/types?engine=escape&kind=formula[&q=mandel]   -- browse: types with counts
```

- `reader` is the version every request states (api-updates.md rule 2):
  only what a reader of that version can open is listed. Absent, it is 3,
  the original vocabulary.
- `GET /api/types` lists types with how many public configs use each, for
  "browse by fractal type" menus. Counts are a `GROUP BY` over
  `flame_components` at first, cached if they get hot.
- List items gain `engine`, `scene`, `dimension`, `min_reader` and the
  primary type, as **new fields**. Old clients ignore them.
